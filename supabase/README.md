# Supabase: база, права и расписание

Это серверная часть сайта. На GitHub Pages публикуется только интерфейс. ФИО, соответствие кодов студентов и роли хранятся в схеме `private` внутри PostgreSQL проекта Supabase.

## Первоначальная настройка

1. Создайте проект Supabase на своём аккаунте. Включите Data API. Автоматически открывать новые таблицы для API не нужно: миграция выдаёт необходимые права явно.
2. В **Authentication → Sign In / Providers** включите **Anonymous Sign-Ins**. Google, почта, телефон и пароли студентам не требуются.
3. В **SQL Editor** выполните файл [`schema.sql`](schema.sql) целиком. Он создаёт группу `SE-2421` с часовым поясом `Asia/Qyzylorda`, но не добавляет вымышленных студентов или предметов.
4. Импортируйте настоящий список студентов, используя [`roster.example.sql`](roster.example.sql) как шаблон. Выполняйте заполненный SQL только в панели Supabase; не сохраняйте реальный список в GitHub. Хотя бы одному человеку задайте роль `admin`.
5. Выполните [`cron.sql`](cron.sql). При необходимости сначала включите **Cron / pg_cron** в разделе интеграций Supabase. Задача запускает SQL раз в пять минут. Повторное выполнение файла с тем же именем задачи обновляет её, а не добавляет дубликат.
6. В интерфейсе проекта скопируйте **Project URL** и **publishable key** (либо старый `anon public key`) в настройки сайта. Они предназначены для браузера. `service_role`, secret key и пароль PostgreSQL в файлы сайта не добавляются.

Только владелец проекта в SQL Editor может вызывать `private.upsert_student`. Браузер не имеет прав на импорт, изменение ролей или чтение таблицы студентов.

## Как устроен вход

Пользователь вводит имя, фамилию, `SE-2421` и индивидуальный код студента. Сайт создаёт техническую anonymous-сессию Supabase и вызывает:

```js
supabase.rpc('sign_in_student', {
  p_first_name: firstName,
  p_last_name: lastName,
  p_group_code: groupCode,
  p_student_code: studentCode
})
```

Сервер проверяет совпадение с предварительно импортированным списком. Регистр и повторные пробелы в ФИО и названии группы не учитываются. Код хранится в базе как SHA-256, а в API-ответы не включается. Для одного auth-пользователя разрешено не более 10 попыток входа за минуту. Ошибочные попытки действительно сохраняются: функция возвращает JSON-ошибку без отката счётчика.

Новая сессия на другом устройстве привязывается к тому же студенту, а не создаёт новый профиль. Ограничение «одна запись в очередь» и кулдаун относятся к студенту и действуют сразу на всех его устройствах.

**Модель доверия:** индивидуальный код студента — идентификатор, а не сильный пароль. Знание чужого кода и ФИО позволит представиться этим человеком. Это сознательно простой вход для своей группы, без Google и почты. Если потребуется подтверждать личность, нужно отдельно добавить личный секрет/PIN или другой способ аутентификации. Роль администратора всегда берётся из приватного списка, а не из данных формы.

## Браузерный API

Основной вызов:

```js
supabase.rpc('queue_api', { p_action: action, p_payload: payload })
```

Действия:

| Действие | `p_payload` | Кто может |
| --- | --- | --- |
| `state` | `{}` | Участник группы |
| `join` | `{ queue_id }` | Записать себя |
| `leave` | `{ queue_id }` | Убрать себя из ожидающих |
| `next` | `{ queue_id, expected_revision }` | Админ |
| `remove_entry` | `{ queue_id, entry_id }` | Админ |
| `close_queue` | `{ queue_id }` | Админ |
| `archive_queue` | `{ queue_id }` | Админ |
| `create_subject` | `{ name }` | Админ |
| `delete_subject` | `{ subject_id }` | Админ |
| `create_queue` | `{ subject_id, starts_at, opens_at?, closes_at?, title? }` | Админ |
| `save_schedule` | `{ id?, subject_id, weekday, local_time, opens_minutes_before, duration_minutes?, enabled }` | Админ |
| `delete_schedule` | `{ schedule_id }` | Админ |

`weekday` — ISO-день недели: понедельник `1`, четверг `4`, воскресенье `7`. `local_time` имеет вид `14:00`. Моменты `starts_at`, `opens_at`, `closes_at` передаются как ISO 8601 со смещением или `Z`. По умолчанию ручная очередь открывается сразу, а закрывается через два часа после начала занятия.

Чтение `state` не ограничено пятисекундным кулдауном. Между изменениями одного студента сервер требует паузу 5 секунд; новый браузер её не обходит. Неверная команда или недостаточные права тоже могут занять этот интервал. Повторный `join` не создаёт новую запись. Для `next` обязательно передаётся актуальный `revision`: два нажатия со старой версией не пропустят следующего человека.

Админ может убрать текущего защищающегося. Следующий при этом остаётся ожидающим до отдельного вызова `next`. `delete_subject` удаляет только данный предмет и его расписания/очереди/записи; список студентов сохраняется. Подтверждение удаления выполняет интерфейс перед вызовом API.

## Ответы и ошибки

Успешный вход, `state` и успешные изменения возвращают один формат:

```text
{
  user: { id, first_name, last_name, group_code, role: "student" | "admin" },
  group: { id, code, timezone, member_count },
  subjects: [{ id, name }],
  queues: [{
    id, subject_id, subject_name, title, starts_at, opens_at, closes_at,
    status: "upcoming" | "open" | "closed", revision,
    current_entry_id, current_student_id,
    entries: [{ id, student_id, first_name, last_name, display_name, position, is_current }],
    my_entry_id, my_position, waiting_count
  }],
  schedules: [{ id, subject_id, subject_name, weekday, local_time,
                opens_minutes_before, duration_minutes, enabled }]
}
```

У текущего защищающегося `position` и `my_position` равны `0`. Ожидающие имеют позиции `1..N`; `waiting_count` исключает текущего. Если студент не записан, `my_entry_id` и `my_position` равны `null`. Архивные очереди и закрытые более семи дней назад в активный ответ не включаются. За один ответ возвращается не более 100 очередей.

Доменные ошибки возвращаются с HTTP 200 в формате:

```json
{ "error": { "code": "COOLDOWN", "retry_after": 5 } }
```

Клиент проверяет и транспортную ошибку `error` Supabase SDK, и `data.error`. Основные коды:

`UNAUTHENTICATED`, `NOT_REGISTERED`, `INVALID_STUDENT`, `RATE_LIMITED`, `COOLDOWN`, `FORBIDDEN`, `INVALID_ACTION`, `INVALID_INPUT`, `DUPLICATE_SUBJECT`, `DUPLICATE_QUEUE`, `DUPLICATE`, `LIMIT_REACHED`, `SUBJECT_NOT_FOUND`, `QUEUE_NOT_FOUND`, `QUEUE_CLOSED`, `QUEUE_NOT_OPEN`, `NOT_JOINED`, `CURRENT_STUDENT_CANNOT_LEAVE`, `QUEUE_CHANGED`, `ENTRY_NOT_FOUND`, `SCHEDULE_NOT_FOUND`.

## Обновления без передачи списка студентов

Публичная таблица `group_revisions` содержит только `group_id`, номер версии и время изменения. Читать её могут только зарегистрированные участники соответствующей группы, что проверяет RLS. Подписка на `UPDATE` с фильтром `group_id=eq.<group.id>` служит сигналом заново прочитать `state`. В Realtime не публикуются коды, ФИО или приватная таблица студентов.

Миграция добавляет эту таблицу в существующую публикацию `supabase_realtime`. Если публикация ещё не была создана, включите Realtime для `group_revisions` через Dashboard. Прямое изменение этой таблицы браузеру запрещено.

## Автоматическое расписание

Для каждого включённого правила сервер заранее создаёт отдельные очереди занятий на период от вчерашнего дня до семи дней вперёд в часовом поясе группы. Записываться можно только после `opens_at`; в интерфейсе будущая очередь имеет статус `upcoming`. Дата и правило уникальны, поэтому повторный запуск Cron не создаёт повторные очереди. Просроченные очереди закрываются. Даже при задержке Cron сервер проверяет `closes_at` при записи и вызове следующего.

При изменении или удалении расписания автоматически заменяются только будущие, ещё не открытые и пустые очереди. Уже открытые или содержащие записи занятия сохраняются; при необходимости админ закрывает их отдельно.

Cron выполняется в Supabase без открытого сайта. При приостановленном Free-проекте база и Cron не работают до возобновления проекта. Расписание учитывает локальный часовой пояс, а не часовой пояс машины пользователя.

## Проверка SQL

`tests/integration.mjs` запускает миграцию в настоящем PostgreSQL-движке PGlite и проверяет права, приватность, логин, лимиты, отображение одного студента на разных устройствах, очередь, старые версии `next`, расписание и удаление предметов.

Тестовый пакет **не нужен сайту**. Установите `@electric-sql/pglite` во временную папку разработки и укажите путь к его `dist/index.js`:

```powershell
$env:PGLITE_MODULE = 'C:\path\to\pglite\dist\index.js'
node supabase\tests\integration.mjs
```

Проверено: **53 assertions в PostgreSQL/PGlite**, включая повторное применение миграции. Supabase Auth в тестах заменён схемой с тем же `auth.uid()`. Расширение `pg_cron`, реальная доставка Realtime и нагрузка с нескольких настоящих соединений требуют проверки в подключённом Supabase-проекте. Корректность конкурирующих записей обеспечивают блокировки строк, транзакции, уникальность `(queue_id, student_id)` и проверка `expected_revision`; отдельный нагрузочный тест ещё не проводился.

Официальные источники: [Anonymous Auth](https://supabase.com/docs/guides/auth/auth-anonymous), [database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Cron](https://supabase.com/docs/guides/cron).
